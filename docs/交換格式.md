# 個人記帳本 API 前後端資料交換格式規範書

本文件為個人記帳系統（`ledger-api`）之前後端資料交換格式規範，提供前端介面實作與資料對接之依據。

---

## 壹、共通規則

1. **固定三鍵外層封裝**
   所有 API 端點之 HTTP 回應主體（Response Body）一律為 JSON 物件，外層固定包含以下三個鍵：
   - `code`（整數）：對應之 HTTP 狀態碼（如 `200`、`201`、`400`、`404`、`500`）。
   - `message`（字串）：說明操作結果或錯誤原因之繁體中文語句（人話），不包含資料庫底層表名、欄位約束或例外類別。
   - `data`（任意型別 / 可為 `null`）：實際承載之業務資料。查詢成功時為物件或清單；若無回傳資料或發生錯誤時固定為 `null`。

2. **HTTP 狀態碼對照表**
   | 狀態碼 | 意義 | 適用情境 | `data` 內容 |
   | :--- | :--- | :--- | :--- |
   | `200 OK` | 成功查詢或成功更新 | 取得單筆、取得清單（含空清單）、修改資料、取得計算型數值 | 物件、清單或計算結果 |
   | `201 Created` | 成功建立新資源 | `POST` 新增資料成功 | 資料庫寫入後之完整資料列 |
   | `400 Bad Request` | 用戶端請求格式或業務約束失敗 | 必填缺漏、格式不合法、名稱重複、金額不大於 0、指向不存在外鍵等 | 固定為 `null` |
   | `404 Not Found` | 找不到指定資源 | 查詢或更新不存在之單筆主鍵（`id`） | 固定為 `null` |
   | `500 Internal Server Error` | 伺服器內部錯誤 | 資料庫連線中斷、非預期系統異常 | 固定為 `null` |

3. **客戶端不送的欄位**
   - 代理主鍵 `id`、建立時間 `created_at`、更新時間 `updated_at` 由伺服器與資料庫端全權管理，客戶端新增（`POST`）或更新（`PATCH`）時**一律不送**；即使客戶端送出，伺服器亦直接忽略不予採用。
   - 發票的 `prize_status` 於建立時預設為 `unchecked`，客戶端不需填寫。
   - 交易的 `voided_at` 僅能透過專門的作廢端點自動打上時間戳記，新增時不可指定。

4. **日期、時間與金額的型別規範**
   - **日期（Date）**：一律以 ISO 8601 之 `YYYY-MM-DD` 格式字串傳遞（例如：`"2026-08-15"`）。
   - **時間戳記（Timestamp）**：一律以帶有 UTC 時區之 ISO 8601 字串表示（例如：`"2026-08-15T08:30:00.000000+00:00"`）。
   - **金額與數值（Amount / Quantity / Price）**：在 JSON 中一律為**數值型別（number）**（如 `70.0`、`200.0`、`10.0`），不以引號字串包裝，防止型別混淆。
   - **匯率（FX Rate）**：對新台幣匯率 `fx_rate_to_twd` 為數值型別，新台幣固定為 `1.0`。

5. **可空欄位（Nullable）在回應中的表現**
   - 可空欄位（如備註 `note`、隨機碼 `random_code`、商家 `merchant` 等）在資料庫中無值時，回應 JSON 中一律明確輸出為 `null`，保持 JSON 鍵結構的一致性，不可省略該鍵。
   - 客戶端在請求時傳入 JSON 的 `null`，其效果與完全省略該鍵相同。

## 貳、資源交換格式、欄位表與成功範例

> 註：以下所有範例之 `id` 均自數字 `1` 起算示意，實際呼叫時請以 API 回傳之 `id` 為準。

### 1. 帳戶 (Accounts)

#### (1) 欄位定義表
| 欄位名稱 | 型別 | 必填/可空 | 說明 |
| :--- | :--- | :--- | :--- |
| `id` | 整數 | 系統產生 | 帳戶唯一識別碼 |
| `name` | 字串 | 必填 | 帳戶名稱（唯一，不重複） |
| `kind` | 字串 | 必填 | 帳戶種類：`cash`（現金）、`bank`（銀行）、`credit_card`（信用卡）、`broker`（券商交割戶） |
| `currency` | 字串 | 必填 | 帳戶計價幣別（3 碼英文字母，預設 `TWD`） |
| `opening_balance` | 數值 | 必填 | 期初餘額（預設 `0.0`） |
| `statement_day` | 整數 | 可空 | 帳單結帳日（1～31） |
| `payment_day` | 整數 | 可空 | 帳單繳款日（1～31） |
| `created_at` | 字串 | 系統產生 | 建立時間戳記 (UTC) |
| `updated_at` | 字串 | 系統產生 | 更新時間戳記 (UTC) |

#### (2) 成功回應範例（建立現金錢包 `POST /api/accounts` 回應 `201 Created`）
```json
{
  "code": 201,
  "message": "帳戶建立成功",
  "data": {
    "id": 1,
    "name": "現金錢包",
    "kind": "cash",
    "currency": "TWD",
    "opening_balance": 0.0,
    "statement_day": null,
    "payment_day": null,
    "created_at": "2026-08-01T02:00:00.000000+00:00",
    "updated_at": "2026-08-01T02:00:00.000000+00:00"
  }
}
```

#### (3) 帳戶餘額查詢回應範例（`GET /api/accounts/1/balance` 回應 `200 OK`）
```json
{
  "code": 200,
  "message": "取得帳戶餘額成功",
  "data": {
    "account_id": 1,
    "name": "現金錢包",
    "currency": "TWD",
    "opening_balance": 0.0,
    "balance": 200.0,
    "original_currency_balance": 200.0,
    "twd_balance": 200.0
  }
}
```

### 5. 統一發票與品項 (Invoices & Invoice Items)

#### (1) 發票欄位定義表
| 欄位名稱 | 型別 | 必填/可空 | 說明 |

| `id` | 整數 | 系統產生 | 發票唯一識別碼 |

| `amount` | 數值 | 必填 | 發票總額（必須大於 0） |
| `kind` | 字串 | 必填 | 發票型態：`paper`（紙本）、`electronic`（電子載具/雲端發票） |

### 6. 開獎期別與開獎對獎 (Draw Periods & Prizes)

#### (1) 欄位定義表
- **開獎期別 (`draw_periods`)**：`id`, `period_key`（例如 `"2026-07"`）, `created_at`, `updated_at`。
- **獎號與獎金 (`draw_prizes`)**：`id`, `draw_period_id`, `tier` (`special`, `grand`, `first`, `second`, `third`, `fourth`, `fifth`, `sixth`, `extra_sixth`), `matching_number`, `amount`（法定中獎金額 $\ge 0$）。

#### (2) 批次對獎回應範例（`POST /api/draw-periods/1/check` 回應 `200 OK`）
```json
{
  "code": 200,
  "message": "對獎完成",
  "data": {
    "checked_count": 12,
    "won_count": 1
  }
}
```

## 參、錯誤回應完整範例（400 與 404）

回應 JSON 中 `data` 一律為 `null`，且絕不出現資料庫內部表名、約束名、SQLSTATE 或堆疊追蹤。

### 1. HTTP 400 Bad Request 回應範例（請求違反業務規則）
```json
{
  "code": 400,
  "message": "帳戶名稱已被使用，請使用其他名稱",
  "data": null
}
```

### 2. HTTP 404 Not Found 回應範例（請求資源不存在）
```json
{
  "code": 404,
  "message": "找不到指定的帳戶",
  "data": null
}
```

## 肆、內部錯誤日誌規範（僅記錄於伺服器端）

所有詳細的例外追蹤、資料庫約束鍵值、SQLSTATE 代碼**嚴格禁止暴露在外部 API 回應 JSON**，僅於後端伺服器內部日誌以結構化 JSON 紀錄。

### 1. 內部日誌物件標準鍵名清單
| 鍵名 | 型別 | 說明 |
| :--- | :--- | :--- |
| `timestamp` | 字串 | 錯誤發生時之 UTC ISO 8601 時間戳記 |
| `level` | 字串 | 日誌層級（`WARN`、`ERROR`、`CRITICAL`） |
| `error_code` | 字串 | 內部標準化錯誤代碼（見下表） |
| `path` | 字串 | 呼叫失敗之 HTTP 請求路徑 |
| `method` | 字串 | 呼叫失敗之 HTTP 請求方法（`GET`、`POST`、`PATCH` 等） |
| `message` | 字串 | 面向使用者之標準人話錯誤描述 |
| `table` | 字串 | 觸發約束之資料庫實體表名（僅日誌保留） |
| `constraint` | 字串 | 違反應約束之資料庫約束名稱（僅日誌保留） |
| `sqlstate` | 字串 | PostgreSQL 標準 SQLSTATE 狀態碼（例如唯一鍵衝突 `23505`） |
| `details` | 字串 | 詳細之例外除錯追蹤或堆疊（Stacktrace） |

### 2. 內部 `error_code` 對照表
| `error_code` | 代表意義 | 對外 HTTP 狀態碼 |
| :--- | :--- | :---: |
| `validation.required_field` | 請求主體缺少必填欄位或欄位為空字串 | 400 |
| `validation.invalid_format` | 格式不合規（如發票號碼非 2 碼英文 + 8 碼數字、日期非 YYYY-MM-DD） | 400 |
| `validation.positive_amount` | 金額、股數或匯率未大於 0 | 400 |
| `conflict.unique_name` | 帳戶或收支分類名稱重複衝突 | 400 |
| `conflict.unique_invoice_number` | 發票號碼重複衝突 | 400 |
| `conflict.unique_market_symbol` | 同一交易市場已有相同代號之投資標的 | 400 |
| `conflict.duplicate_prize_claim` | 發票已領取過獎金，拒絕重複領獎入帳 | 400 |
| `business.same_account_transfer` | 資金移轉之轉出與轉入為同一帳戶 | 400 |
| `business.empty_source_and_note` | 入帳之來源與備註（或花費之商家與備註）同時為空 | 400 |
| `business.insufficient_holding` | 賣出或減資股數超過當前實際持有股數 | 400 |
| `business.trade_has_income` | 投資交易已綁定入帳記錄，拒絕執行作廢 | 400 |
| `resource.not_found` | 找不到指定 ID 之實體資料 | 404 |
| `database.connection_error` | 資料庫連線失敗或逾時 | 500 |

### 3. `conflict.unique_name` 伺服器內部日誌範例
```json
{
  "timestamp": "2026-11-14T07:10:00.123456+00:00",
  "level": "ERROR",
  "error_code": "conflict.unique_name",
  "path": "/api/accounts",
  "method": "POST",
  "message": "帳戶名稱已被使用，請使用其他名稱",
  "table": "accounts",
  "constraint": "accounts_name_key",
  "sqlstate": "23505",
  "details": "UniqueViolation: duplicate key value violates unique constraint \"accounts_name_key\""
}
```
> **注意**：上述日誌物件中之 `table`、`constraint`、`sqlstate`、`details` 絕不出現在回應客戶端的 JSON 中。

## 陸、與現況的差異

本節逐條整理現有 Python 程式碼實作與步驟 14 約定之間的細部差異，供日後維護參考（現有後端程式碼維持現狀，不作改動）：

| 端點 / 模組 | 現況實作行為 | 步驟 14 的約定 | 說明與差異註記 |
| :--- | :--- | :--- | :--- |
| `GET /api/accounts/<id>/balance` | `data` 物件回傳包含 `balance`、`original_currency_balance` 與 `twd_balance` | 規範主要要求台幣餘額與原幣別餘額 | 現況為求相容性，同時提供 `balance`（等同原幣別餘額）與明確命名之 `twd_balance` |
| `GET /api/invoices/<id>` | `data` 物件中掛接的花費清單鍵名為 `expense_ids`（整數 ID 陣列） | 規範約定在 `data` 帶上「已掛上的花費 id 清單」 | 現況以 `expense_ids: [1, 2]` 清晰陣列呈現，符合約定意圖 |
| `GET /api/summary` | 若無任何紀錄時，回傳 `{"month": "YYYY-MM", "income_twd": 0.0, "expense_twd": 0.0}` | 規範約定該月沒有任何列時合計為 0，HTTP 狀態碼為 200 | 現況實作與約定完全一致，數值採浮點 `0.0` 呈現 |
| `POST /api/trades` | 支援 `post_income` 參數（布林值），當為 `true` 時需傳入 `income_category_id` | 規範約定同筆資料庫交易建立 `incomes` 且必填 `income_category_id` | 現況以 `db.session.flush()` 與原子性提交達成，完全符合約定 |
