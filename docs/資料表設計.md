# 個人記帳系統資料表設計規格書 (PostgreSQL on Supabase)

本文件為個人專用記帳系統之資料庫設計規格，資料庫引擎採用 Supabase 託管之 PostgreSQL。

---

## 壹、全域設計規範與共通約定

1. **主鍵設計規範**
   - 全系統資料表主鍵統一命名為 `id`。
   - 型別一律採用 64 位元整數 `bigint`，並由資料庫端以 `GENERATED ALWAYS AS IDENTITY` 自動產生，建立後不可竄改與重複。
2. **時間欄位與時區規範**
   - 涉及時間之欄位統一採用 `timestamptz`（帶時區之時間戳記）。
   - 每一張資料表均包含以下兩項時間追蹤欄位：
     - `created_at`：`timestamptz NOT NULL DEFAULT (now() AT TIME ZONE 'utc')`，資料插入時由資料庫自動填入當前 UTC 時間。
     - `updated_at`：`timestamptz NOT NULL`，資料更新時由後端應用程式（API）明確寫入更新時之 UTC 時間。
3. **金額、幣別與匯率規範**
   - 金額與股數均使用精確數值型別 `numeric`，以避免浮點數精度損失。
   - 幣別代碼統一採用 ISO 4217 三碼大寫英文字元 `char(3)`（例如：`TWD`、`USD`、`JPY`）。
   - 外幣交易均記錄換算為新台幣之匯率 `twd_exchange_rate`（型別為 `numeric(12, 6)`，必大於 0）。
   - 若幣別為 `TWD`，匯率必須嚴格等於 1。
4. **外鍵約束與刪除防護規範**
   - 父列（被參照列）仍有子列參照時，嚴格禁止刪除，所有外鍵預設強制設定為 `ON DELETE RESTRICT`（或 `ON DELETE NO ACTION`）。
   - **全系統唯一刪除例外**：僅「發票品項（`invoice_items`）」隸屬於「統一發票（`invoices`）」；當發票被刪除時，其所屬品項一律隨之消失，該外鍵設定為 `ON DELETE CASCADE`。
5. **分類隔離原則**
   - 入帳分類與花費分類採用完全獨立之資料表，兩者各自命名且名稱不可重複。
6. **非持久化衍生數值規範**
   - 帳戶「餘額」與投資「持有股數／平均成本」均不建立可直接修改之欄位，由底層交易明細列依時間順序動態聚合計算，確保資料一致性與不可篡改性。
7. **規則落地責任劃分**
   - 所有資料完整性規則，優先使用 PostgreSQL 的 `CHECK`、`FOREIGN KEY`、`UNIQUE` 等約束實現；涉及跨多列彙總或動態庫存驗證之規則，明確標記為「由 API 在寫入前檢查」。

## 貳、資料表詳細規格

### 1. 帳戶表 `accounts`

#### (1) 表在記什麼與為什麼單獨成表
- **記什麼**：記錄所有個人資金所歸屬的實體或虛擬載體，包含現金口袋、銀行活存、信用卡、券商交割戶等。
- **為什麼單獨成表**：資金必須落於明確的帳戶實體，且不同類型帳戶具備不同之清算特性（例如：信用卡具負債與延後結算特質、券商交割戶與投資交易緊密聯動）。將帳戶獨立成表可作為所有資金流向（入帳、花費、移轉、證券交割）的核心錨點，避免將帳戶名稱與屬性硬編碼於交易明細中。

#### (2) 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | 唯一 (PK) | 主鍵，資料庫自動產生，不可修改 |
| `name` | `varchar(50)` | 必填 | 唯一 (UNIQUE) | 帳戶名稱（如：台新 Richart、中信 LINE Pay 卡、日常現金包） |
| `account_type` | `varchar(30)` | 必填 | 非唯一 | 帳戶型態：`cash`（現金）、`bank`（銀行）、`credit_card`（信用卡）、`brokerage_settlement`（券商交割戶） |
| `currency` | `char(3)` | 必填 | 非唯一 | 帳戶主要結算幣別（如：`TWD`、`USD`） |
| `is_active` | `boolean` | 必填 | 非唯一 | 帳戶是否啟用（預設 `true`） |
| `note` | `text` | 可空 | 非唯一 | 備註說明 |
| `created_at` | `timestamptz` | 必填 | 非唯一 | 建立時間，資料庫預設 UTC 時間 |
| `updated_at` | `timestamptz` | 必填 | 非唯一 | 更新時間，由應用程式更新 |

#### (3) 鍵與約束規則
- **主鍵**：`PRIMARY KEY (id)`。
- **外鍵**：無。
- **PostgreSQL 約束**：
  - `CHECK (account_type IN ('cash', 'bank', 'credit_card', 'brokerage_settlement'))`：限定帳戶型態。
  - `CHECK (currency ~ '^[A-Z]{3}$')`：限定三碼大寫英文字元。
  - `UNIQUE (name)`：帳戶名稱不得重複。
- **API 檢查責任**：停用帳戶前，應檢查該帳戶餘額是否已結清。

### 4. 入帳表 `incomes`

#### (1) 表在記什麼與為什麼單獨成表
- **記什麼**：記錄實質資金流入個人的事件（入帳冊）。涵蓋薪水、獎金、利息、退款，以及發票中獎獎金、投資產生的現金股利與減資退回款項。
- **為什麼單獨成表**：入帳代表淨資產的正向增加，具備明確的資金注入帳戶、入帳時間與匯率換算。將其單獨成表能與花費、內部帳戶移轉乾淨切分，並能精確串接發票中獎與投資收益。

#### (2) 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | 唯一 (PK) | 主鍵，資料庫自動產生，不可修改 |
| `account_id` | `bigint` | 必填 | 非唯一 | 資金存入之帳戶 ID |
| `category_id` | `bigint` | 必填 | 非唯一 | 入帳分類 ID |
| `amount` | `numeric(16, 4)` | 必填 | 非唯一 | 入帳原始幣別金額（必須大於 0） |
| `currency` | `char(3)` | 必填 | 非唯一 | 入帳幣別代碼 |
| `twd_exchange_rate` | `numeric(12, 6)` | 必填 | 非唯一 | 換算為新台幣之匯率（TWD 時必須為 1） |
| `received_at` | `timestamptz` | 必填 | 非唯一 | 實際入帳日與時間 |
| `invoice_id` | `bigint` | 可空 | 唯一 (UNIQUE) | 關聯之統一發票 ID（中獎入帳使用，一張發票最多一筆） |
| `investment_transaction_id` | `bigint` | 可空 | 唯一 (UNIQUE) | 關聯之投資交易 ID（股利/減資退款使用，一筆交易最多一筆） |
| `note` | `text` | 可空 | 非唯一 | 備註說明 |
| `created_at` | `timestamptz` | 必填 | 非唯一 | 建立時間，資料庫預設 UTC 時間 |
| `updated_at` | `timestamptz` | 必填 | 非唯一 | 更新時間，由應用程式更新 |

#### (3) 鍵與約束規則
- **主鍵**：`PRIMARY KEY (id)`。
- **外鍵**：
  - `FOREIGN KEY (account_id) REFERENCES accounts(id) ON DELETE RESTRICT`。
  - `FOREIGN KEY (category_id) REFERENCES income_categories(id) ON DELETE RESTRICT`。
  - `FOREIGN KEY (invoice_id) REFERENCES invoices(id) ON DELETE RESTRICT`。
  - `FOREIGN KEY (investment_transaction_id) REFERENCES investment_transactions(id) ON DELETE RESTRICT`。
- **PostgreSQL 約束**：
  - `CHECK (amount > 0)`：金額必須大於 0。
  - `CHECK (twd_exchange_rate > 0)`：匯率必須大於 0。
  - `CHECK ((currency = 'TWD' AND twd_exchange_rate = 1.0) OR (currency <> 'TWD'))`：新台幣匯率強制為 1。
  - `UNIQUE (invoice_id)`：強制保證一張統一發票最多只能產生一筆入帳。
  - `UNIQUE (investment_transaction_id)`：強制保證一筆投資交易最多只能產生一筆入帳。
- **API 檢查責任**：
  - 若 `invoice_id` 非空，需檢查該發票是否確認已中獎，且入帳金額應等於該發票對應獎項之獎金金額。
  - 若 `investment_transaction_id` 非空，需檢查該筆交易類別必須為 `cash_dividend`（現金股利）或 `capital_reduction`（減資退回現金），且入帳金額需等於交易之淨現金回流額。

### 5. 花費表 `expenses`

#### (1) 表在記什麼與為什麼單獨成表
- **記什麼**：記錄實質資金流出個人的消費事件（花費冊）。記載消費實際發生時間、扣款/帳單時間、支付帳戶、金額與幣別。
- **為什麼單獨成表**：花費為個人淨資產的流出核心。現實消費中，消費行為發生日與實際扣款日經常不同（如信用卡刷卡當下為消費日，次月結帳扣款日才是扣款日），獨立設表可精準支持雙時間戳記，並能與統一發票形成多對一的彈性關聯。

#### (2) 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | 唯一 (PK) | 主鍵，資料庫自動產生，不可修改 |
| `account_id` | `bigint` | 必填 | 非唯一 | 扣款或支付帳戶 ID |
| `category_id` | `bigint` | 必填 | 非唯一 | 花費分類 ID |
| `amount` | `numeric(16, 4)` | 必填 | 非唯一 | 花費金額（必須大於 0） |
| `currency` | `char(3)` | 必填 | 非唯一 | 花費幣別代碼 |
| `twd_exchange_rate` | `numeric(12, 6)` | 必填 | 非唯一 | 換算為新台幣之匯率（TWD 時必須為 1） |
| `spent_at` | `timestamptz` | 必填 | 非唯一 | 消費發生日（刷卡日、付現日） |
| `billed_at` | `timestamptz` | 可空 | 非唯一 | 帳戶扣款日（如信用卡扣款結算日，付現時通常與 `spent_at` 相同或留空） |
| `invoice_id` | `bigint` | 可空 | 非唯一 | 關聯之統一發票 ID（一張發票可對應多筆花費） |
| `note` | `text` | 可空 | 非唯一 | 備註說明 |
| `created_at` | `timestamptz` | 必填 | 非唯一 | 建立時間，資料庫預設 UTC 時間 |
| `updated_at` | `timestamptz` | 必填 | 非唯一 | 更新時間，由應用程式更新 |

#### (3) 鍵與約束規則
- **主鍵**：`PRIMARY KEY (id)`。
- **外鍵**：
  - `FOREIGN KEY (account_id) REFERENCES accounts(id) ON DELETE RESTRICT`。
  - `FOREIGN KEY (category_id) REFERENCES expense_categories(id) ON DELETE RESTRICT`。
  - `FOREIGN KEY (invoice_id) REFERENCES invoices(id) ON DELETE RESTRICT`。
- **PostgreSQL 約束**：
  - `CHECK (amount > 0)`：花費金額必須大於 0。
  - `CHECK (twd_exchange_rate > 0)`：匯率必須大於 0。
  - `CHECK ((currency = 'TWD' AND twd_exchange_rate = 1.0) OR (currency <> 'TWD'))`：新台幣匯率強制為 1。
- **業務規則說明**：
  - `invoice_id` 未設唯一約束，允許多筆花費對應同一張發票（例如：一張超市發票拆分「食材花費」與「日用品花費」）。
  - 花費金額合計不必等於發票總額（例如：他人代墊部分、折價券折抵、或是只報銷或記錄個人自用部分）。
- **API 檢查責任**：若為信用卡帳戶且填寫 `billed_at`，檢查 `billed_at` 日期不得早於 `spent_at`。

### 6. 帳戶移轉表 `transfers`

#### (1) 表在記什麼與為什麼單獨成表
- **記什麼**：記錄自自有甲帳戶將資金移至自有乙帳戶的過程（例如：ATM 提款至現金包、銀行轉帳至券商交割戶、銀行扣款繳納信用卡費）。
- **為什麼單獨成表**：移轉本質為「資產重分類」或「負債償還」，既不是收入也不是花費，不改變個人淨資產總值。若混入入帳或花費表會嚴重失真收支統計，故必須單獨成表。

#### (2) 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | 唯一 (PK) | 主鍵，資料庫自動產生，不可修改 |
| `from_account_id` | `bigint` | 必填 | 非唯一 | 轉出資金之來源帳戶 ID |
| `to_account_id` | `bigint` | 必填 | 非唯一 | 轉入資金之目的帳戶 ID |
| `from_amount` | `numeric(16, 4)` | 必填 | 非唯一 | 轉出金額（必須大於 0） |
| `to_amount` | `numeric(16, 4)` | 必填 | 非唯一 | 轉入金額（必須大於 0，跨幣別換匯或有手續費時可能不同） |
| `from_currency` | `char(3)` | 必填 | 非唯一 | 轉出幣別代碼 |
| `to_currency` | `char(3)` | 必填 | 非唯一 | 轉入幣別代碼 |
| `twd_exchange_rate` | `numeric(12, 6)` | 必填 | 非唯一 | 轉出幣別換算為新台幣之匯率（TWD 時必須為 1） |
| `transferred_at` | `timestamptz` | 必填 | 非唯一 | 資金移轉完成時間 |
| `note` | `text` | 可空 | 非唯一 | 備註說明（如：繳納信用卡費、換匯等） |
| `created_at` | `timestamptz` | 必填 | 非唯一 | 建立時間，資料庫預設 UTC 時間 |
| `updated_at` | `timestamptz` | 必填 | 非唯一 | 更新時間，由應用程式更新 |

#### (3) 鍵與約束規則
- **主鍵**：`PRIMARY KEY (id)`。
- **外鍵**：
  - `FOREIGN KEY (from_account_id) REFERENCES accounts(id) ON DELETE RESTRICT`。
  - `FOREIGN KEY (to_account_id) REFERENCES accounts(id) ON DELETE RESTRICT`。
- **PostgreSQL 約束**：
  - `CHECK (from_account_id <> to_account_id)`：轉出與轉入帳戶不能為同一個帳戶。
  - `CHECK (from_amount > 0 AND to_amount > 0)`：金額必須大於 0。
  - `CHECK (twd_exchange_rate > 0)`：匯率必須大於 0。
  - `CHECK ((from_currency = 'TWD' AND twd_exchange_rate = 1.0) OR (from_currency <> 'TWD'))`：台幣轉出匯率強制為 1。
- **API 檢查責任**：
  - 同幣別移轉時，若無外扣手續費，檢查 `from_amount` 是否等於 `to_amount`；如有跨行手續費，手續費應另外作為一筆關聯之 `expenses`（手續費花費）記錄。
  - 轉出帳戶餘額是否充裕之風險提示。

### 7. 統一發票表 `invoices`

#### (1) 表在記什麼與為什麼單獨成表
- **記什麼**：記錄台灣統一發票憑證本體資訊（發票冊），包含兩碼英文八碼數字之號碼、開立日、雙月期別、發票金額、開立商家統編與中獎獎項。
- **為什麼單獨成表**：統一發票為台灣法定報稅與公辦對獎單據。一張發票可能包含多個商品細項，亦可能對應零筆、一筆或多筆花費；發票本身具有雙月對獎的獨立生命週期，故必須獨立成表。

#### (2) 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | 唯一 (PK) | 主鍵，資料庫自動產生，不可修改 |
| `invoice_number` | `varchar(10)` | 必填 | 唯一 (UNIQUE) | 發票號碼：2 碼大寫英文字母 + 8 碼數字 |
| `issued_at` | `timestamptz` | 必填 | 非唯一 | 發票開立日期與時間 |
| `period` | `char(6)` | 必填 | 非唯一 | 發票期別（西元年 4 碼 + 雙月雙數月份 2 碼，如 `202602`） |
| `total_amount` | `numeric(16, 4)` | 必填 | 非唯一 | 發票票面總金額（必須大於或等於 0） |
| `seller_tax_id` | `varchar(8)` | 可空 | 非唯一 | 賣方統一編號（8 碼數字） |
| `seller_name` | `varchar(100)` | 可空 | 非唯一 | 賣方商店名稱 |
| `buyer_tax_id` | `varchar(8)` | 可空 | 非唯一 | 買方統一編號（個人打統編時記錄） |
| `prize_tier_id` | `bigint` | 可空 | 非唯一 | 中獎獎項 ID（外鍵關聯至獎金定義表，未中獎或未開獎時為空） |
| `note` | `text` | 可空 | 非唯一 | 備註說明 |
| `created_at` | `timestamptz` | 必填 | 非唯一 | 建立時間，資料庫預設 UTC 時間 |
| `updated_at` | `timestamptz` | 必填 | 非唯一 | 更新時間，由應用程式更新 |

#### (3) 鍵與約束規則
- **主鍵**：`PRIMARY KEY (id)`。
- **外鍵**：
  - `FOREIGN KEY (prize_tier_id) REFERENCES invoice_prize_tiers(id) ON DELETE RESTRICT`。
- **PostgreSQL 約束**：
  - `UNIQUE (invoice_number)`：發票號碼不得重複。
  - `CHECK (invoice_number ~ '^[A-Z]{2}[0-9]{8}$')`：嚴格限制格式為兩碼大寫英文與八碼數字。
  - `CHECK (total_amount >= 0)`：發票總額不可小於 0。
  - `CHECK (period ~ '^[0-9]{4}(02|04|06|08|10|12)$')`：期別必須為合法的西元年加偶數月（02, 04, 06, 08, 10, 12）。
  - `CHECK (seller_tax_id IS NULL OR seller_tax_id ~ '^[0-9]{8}$')`：統編為 8 碼數字。
- **期別產生與 API 檢查責任**：
  - **由 API 在寫入前檢查與計算**：發票的 `period` 必須嚴格由 `issued_at` 計算填入，公式與規則詳見【肆、統一發票期別與獎金處理機制】。API 寫入時需驗證送入的 `period` 與 `issued_at` 是否吻合。

### 8. 發票品項表 `invoice_items`

#### (1) 表在記什麼與為什麼單獨成表
- **記什麼**：記錄一張統一發票清單上的各別明細品項，如購買品名、數量、單價與小計金額。
- **為什麼單獨成表**：實體發票具有一對多的明細清單結構，品項展開便於未來核對消費內容與特定商品價格走勢，避免在發票主表中以不正規劃的字串或 JSON 混合儲存。

#### (2) 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | 唯一 (PK) | 主鍵，資料庫自動產生，不可修改 |
| `invoice_id` | `bigint` | 必填 | 非唯一 | 所屬統一發票 ID |
| `item_name` | `varchar(200)` | 必填 | 非唯一 | 品項名稱（商品或服務說明） |
| `quantity` | `numeric(12, 4)` | 必填 | 非唯一 | 數量（必須大於 0） |
| `unit_price` | `numeric(16, 4)` | 必填 | 非唯一 | 單價 |
| `subtotal` | `numeric(16, 4)` | 必填 | 非唯一 | 小計金額 |
| `note` | `text` | 可空 | 非唯一 | 品項備註 |
| `created_at` | `timestamptz` | 必填 | 非唯一 | 建立時間，資料庫預設 UTC 時間 |
| `updated_at` | `timestamptz` | 必填 | 非唯一 | 更新時間，由應用程式更新 |

#### (3) 鍵與約束規則
- **主鍵**：`PRIMARY KEY (id)`。
- **外鍵**：
  - `FOREIGN KEY (invoice_id) REFERENCES invoices(id) ON DELETE CASCADE`。
  - **重要特別規定**：此為全系統**唯一允許串聯刪除（CASCADE）**的外鍵約束。當父層統一發票（`invoices`）被刪除時，其所屬品項明細隨同一起消失；其餘所有資料表均禁止 CASCADE。
- **PostgreSQL 約束**：
  - `CHECK (quantity > 0)`：數量必須大於 0。
- **API 檢查責任**：品項之小計與發票總金額核對可提示使用者，但因折讓、促銷減免或含稅捨入差異，不強制限制小計總和絕對等於發票總金額。

### 9. 發票開獎期別與中獎號碼表 `invoice_draws`

#### (1) 表在記什麼與為什麼單獨成表
- **記什麼**：記錄財政部每期（雙月）開出的統一發票正式獎號，包括開獎日、特別獎、特獎、頭獎（多組 8 碼）、增開六獎等號碼。
- **為什麼單獨成表**：開獎號碼屬於客觀的外部期別標準資料，每兩個月產生一組開獎結果。將其獨立成表，使得自動化對獎邏輯可以純粹經由比對資料庫資料完成，不必在後端程式碼中硬編碼號碼。

#### (2) 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | 唯一 (PK) | 主鍵，資料庫自動產生，不可修改 |
| `period` | `char(6)` | 必填 | 唯一 (UNIQUE) | 開獎期別（如 `202602`），一期僅一筆開獎紀錄 |
| `draw_date` | `date` | 必填 | 非唯一 | 開獎日期（通常為次月 25 日，例如 1-2 月期於 3 月 25 日開獎） |
| `special_prize_number` | `varchar(8)` | 必填 | 非唯一 | 特別獎號碼（8 碼數字） |
| `grand_prize_number` | `varchar(8)` | 必填 | 非唯一 | 特獎號碼（8 碼數字） |
| `first_prize_numbers` | `varchar(100)` | 必填 | 非唯一 | 頭獎號碼（3 組 8 碼數字，以半形逗點分隔，如 `12345678,23456789,34567890`） |
| `additional_sixth_prize_numbers` | `varchar(50)` | 可空 | 非唯一 | 增開六獎末 3 碼（多組以逗點分隔；無增開時為空） |
| `note` | `text` | 可空 | 非唯一 | 開獎備註說明 |
| `created_at` | `timestamptz` | 必填 | 非唯一 | 建立時間，資料庫預設 UTC 時間 |
| `updated_at` | `timestamptz` | 必填 | 非唯一 | 更新時間，由應用程式更新 |

#### (3) 鍵與約束規則
- **主鍵**：`PRIMARY KEY (id)`。
- **外鍵**：無。
- **PostgreSQL 約束**：
  - `UNIQUE (period)`：同一個發票期別只能有一筆開獎號碼資料。
  - `CHECK (period ~ '^[0-9]{4}(02|04|06|08|10|12)$')`：期別格式校驗。
  - `CHECK (special_prize_number ~ '^[0-9]{8}$')`：特別獎為 8 碼數字。
  - `CHECK (grand_prize_number ~ '^[0-9]{8}$')`：特獎為 8 碼數字。
- **API 檢查責任**：驗證頭獎與增開獎之格式與組數是否合規。

### 10. 發票獎項與獎金定義表 `invoice_prize_tiers`

#### (1) 表在記什麼與為什麼單獨成表
- **記什麼**：記錄統一發票各獎項名稱、中獎規則代碼以及**各獎項對應之開獎獎金金額**。
- **為什麼單獨成表**：本設計嚴格落實「**開獎獎金放在資料表，不寫死在設計說明的程式片段裡**」。獎金金額屬於可變政策參數（例如特別獎 1,000 萬元、特獎 200 萬元、頭獎 20 萬元、六獎 200 元等）。獨立建表後，若法規調整獎金或增設獎項，只需於資料庫新增或調整列，業務邏輯程式完全無需重構修改。

#### (2) 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | 唯一 (PK) | 主鍵，資料庫自動產生，不可修改 |
| `tier_code` | `varchar(30)` | 必填 | 唯一 (UNIQUE) | 獎項代碼（如：`special_prize`、`grand_prize`、`first_prize`、`second_prize`、`third_prize`、`fourth_prize`、`fifth_prize`、`sixth_prize`） |
| `tier_name` | `varchar(50)` | 必填 | 非唯一 | 獎項中文名稱（如：特別獎、特獎、頭獎、二獎、三獎、四獎、五獎、六獎） |
| `reward_amount` | `numeric(16, 4)` | 必填 | 非唯一 | 該獎項之法定中獎獎金金額（新台幣元） |
| `match_rule_description` | `text` | 必填 | 非唯一 | 對獎規則說明（如：同期 8 位數號碼全中、末 7 碼相同等） |
| `created_at` | `timestamptz` | 必填 | 非唯一 | 建立時間，資料庫預設 UTC 時間 |
| `updated_at` | `timestamptz` | 必填 | 非唯一 | 更新時間，由應用程式更新 |

#### (3) 鍵與約束規則
- **主鍵**：`PRIMARY KEY (id)`。
- **外鍵**：無。
- **PostgreSQL 約束**：
  - `UNIQUE (tier_code)`：獎項代碼不得重複。
  - `CHECK (reward_amount >= 0)`：獎金金額不得小於 0。
- **API 檢查責任**：對獎完成判定中獎等級後，直接讀取本表對應之 `reward_amount` 產生入帳明細，不得於程式端 hard-code 獎金常數。

### 11. 投資標的表 `investment_targets`

#### (1) 表在記什麼與為什麼單獨成表
- **記什麼**：記錄所有個人持有的投資商品基礎資料（投資冊標的實體），如股票、ETF 等之代號、名稱、發行市場與計價幣別。
- **為什麼單獨成表**：落實「投資記一檔標的與每一筆交易」之規範。標的本身是交易的載體，將其獨立成表可統一標的命名、管理市場代號，並確保交易流水能穩定關聯至單一標的。持有股數與平均成本不在此表開欄位，完全由交易明細動態演算。

#### (2) 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | 唯一 (PK) | 主鍵，資料庫自動產生，不可修改 |
| `symbol` | `varchar(20)` | 必填 | 唯一 (UNIQUE) | 標的代號（如：`2330`、`0050`、`VOO`、`VT`） |
| `name` | `varchar(100)` | 必填 | 非唯一 | 標的名稱（如：台積電、元大台灣50、Vanguard S&P 500 ETF） |
| `asset_type` | `varchar(30)` | 必填 | 非唯一 | 資產類別：`stock`（股票）、`etf`（指數股票型基金）、`fund`（基金）、`other`（其他） |
| `currency` | `char(3)` | 必填 | 非唯一 | 計價主要幣別（如：`TWD`、`USD`） |
| `market` | `varchar(30)` | 可空 | 非唯一 | 交易市場（如：`TWSE`、`TPEx`、`NYSE`、`NASDAQ`） |
| `note` | `text` | 可空 | 非唯一 | 標的備註說明 |
| `created_at` | `timestamptz` | 必填 | 非唯一 | 建立時間，資料庫預設 UTC 時間 |
| `updated_at` | `timestamptz` | 必填 | 非唯一 | 更新時間，由應用程式更新 |

#### (3) 鍵與約束規則
- **主鍵**：`PRIMARY KEY (id)`。
- **外鍵**：無。
- **PostgreSQL 約束**：
  - `UNIQUE (symbol)`：標的代號必須唯一。
  - `CHECK (asset_type IN ('stock', 'etf', 'fund', 'other'))`：限定資產型態。
  - `CHECK (currency ~ '^[A-Z]{3}$')`：幣別限定三碼大寫英文字元。
- **API 檢查責任**：若該標的尚有歷史交易明細，禁止從標的表刪除（外鍵 RESTRICT 亦會聯防）。

### 12. 投資交易表 `investment_transactions`

#### (1) 表在記什麼與為什麼單獨成表
- **記什麼**：記錄標的的每一筆具體異動事件，完整支援 8 種核心交易型態：
  1. `buy`：買進
  2. `sell`：賣出
  3. `cash_dividend`：現金股利
  4. `stock_dividend`：配股（股票股利）
  5. `dividend_reinvestment`：股息再投入
  6. `split`：股票分割
  7. `reverse_split`：股票合併
  8. `capital_reduction`：減資（退還股款或彌補虧損）
- **為什麼單獨成表**：投資標的的持有股數、剩餘庫存、持股平均成本完全是歷史交易事件流疊加的結果。只有將每一筆異動獨立成不可變更的事件紀錄列，才能精準還原歷史損益、計算除權息與分割調整。

#### (2) 欄位定義
| 欄位名稱 | 型別 | 必填/可空 | 唯一性 | 說明 |
| :--- | :--- | :--- | :--- | :--- |
| `id` | `bigint` | 必填 | 唯一 (PK) | 主鍵，資料庫自動產生，不可修改 |
| `target_id` | `bigint` | 必填 | 非唯一 | 關聯之投資標的 ID |
| `account_id` | `bigint` | 可空 | 非唯一 | 關聯之券商交割戶帳戶 ID（涉及現金結算時必填；純配股、分割、合併時可為空） |
| `transaction_type` | `varchar(30)` | 必填 | 非唯一 | 交易種類（詳見交易類別約束清單） |
| `transacted_at` | `timestamptz` | 必填 | 非唯一 | 交易成交或生效日期時間 |
| `shares` | `numeric(16, 6)` | 必填 | 非唯一 | 異動或涉及股數（必須大於或等於 0，無股數變動之純現金股利為 0） |
| `price_per_share` | `numeric(16, 6)` | 必填 | 非唯一 | 每股價格或每股配息金額（必須大於或等於 0） |
| `fee` | `numeric(16, 4)` | 必填 | 非唯一 | 手續費（必須大於或等於 0，預設 0） |
| `tax` | `numeric(16, 4)` | 必填 | 非唯一 | 證券交易稅或預扣所得稅（必須大於或等於 0，預設 0） |
| `net_cash_amount` | `numeric(16, 4)` | 必填 | 非唯一 | 該筆交易帶來的淨現金收付額（買進為交割付出，賣出/股息/減資為收取，純換股為 0） |
| `currency` | `char(3)` | 必填 | 非唯一 | 結算幣別代碼 |
| `twd_exchange_rate` | `numeric(12, 6)` | 必填 | 非唯一 | 結算幣別換算為新台幣之匯率（TWD 時必須為 1） |
| `split_ratio_from` | `numeric(12, 6)` | 可空 | 非唯一 | 分割／合併／減資之基準股數前值（例如 1 股拆為 2 股時為 1） |
| `split_ratio_to` | `numeric(12, 6)` | 可空 | 非唯一 | 分割／合併／減資之換算股數後值（例如 1 股拆為 2 股時為 2） |
| `note` | `text` | 可空 | 非唯一 | 交易備註說明 |
| `created_at` | `timestamptz` | 必填 | 非唯一 | 建立時間，資料庫預設 UTC 時間 |
| `updated_at` | `timestamptz` | 必填 | 非唯一 | 更新時間，由應用程式更新 |

#### (3) 鍵與約束規則
- **主鍵**：`PRIMARY KEY (id)`。
- **外鍵**：
  - `FOREIGN KEY (target_id) REFERENCES investment_targets(id) ON DELETE RESTRICT`。
  - `FOREIGN KEY (account_id) REFERENCES accounts(id) ON DELETE RESTRICT`。
- **PostgreSQL 約束**：
  - `CHECK (transaction_type IN ('buy', 'sell', 'cash_dividend', 'stock_dividend', 'dividend_reinvestment', 'split', 'reverse_split', 'capital_reduction'))`：交易類型白名單校驗。
  - `CHECK (shares >= 0)`：股數不可為負數。
  - `CHECK (price_per_share >= 0)`：單價不可為負數。
  - `CHECK (fee >= 0 AND tax >= 0)`：費用不可為負數。
  - `CHECK (twd_exchange_rate > 0)`：匯率必須大於 0。
  - `CHECK ((currency = 'TWD' AND twd_exchange_rate = 1.0) OR (currency <> 'TWD'))`：台幣匯率強制為 1。
  - `CHECK ((split_ratio_from IS NULL AND split_ratio_to IS NULL) OR (split_ratio_from > 0 AND split_ratio_to > 0))`：分割比率必須成對且大於 0。
- **關鍵業務約束（賣出不得使持有小於 0）**：
  - **由 API 在寫入前檢查**：由於檢查某一筆賣出交易是否會導致持有股數為負數，涉及針對特定標的在成交時間點以前的所有歷史異動紀錄累加計算，無法使用單一資料列的 `CHECK` 約束達成。
  - **檢查實作要求**：API 在寫入 `sell` 交易時，必須在同一個資料庫交易事務（Transaction）內，對該標的加鎖（例如使用 `SELECT ... FOR UPDATE` 鎖定歷史交易），重新計算截至目前為止的總持有股數，嚴格確認 `當前總持有股數 - 欲賣出股數 >= 0` 始可提交，否則拒絕寫入。
- **現金股利與減資退款之入帳關聯規則**：
  - 若交易為 `cash_dividend` 或包含退回股款之 `capital_reduction`，當此筆現金匯入交割帳戶時，應在 `incomes` 表中新增一筆入帳，並將該入帳列的 `investment_transaction_id` 指向本筆交易 ID。
  - 由於 `incomes.investment_transaction_id` 在資料庫層設有 `UNIQUE` 約束，直接從資料庫底層強制保證：**一筆投資交易最多只能產生一筆入帳**。

## 參、計算型數值之衍生邏輯說明

依據規範，帳戶「餘額」與投資「持有股數／平均成本」均不設計為可直接修改之欄位，以避免人為覆寫造成歷史紀錄矛盾。以下為其精確計算衍生來源：

### 1. 帳戶餘額（Account Balance）衍生邏輯

針對特定帳戶（給定 `account_id`），其當前餘額等於該帳戶歷史所有交易流水之加減總和：

$$\text{餘額} = \sum(\text{入帳}) + \sum(\text{轉入}) - \sum(\text{花費}) - \sum(\text{轉出}) + \sum(\text{投資買賣與現金流結算})$$

#### (1) 各交易表之具體列來源
1. **入帳表（`incomes`）**：
   - 篩選 `incomes.account_id = target_account_id`
   - 增加金額：$+\sum(\text{amount})$
   - 包含：薪資、一般入帳、發票中獎（`invoice_id` 關聯之入帳）、以及現金股利／減資退款（`investment_transaction_id` 關聯之入帳）。
2. **轉入款項（`transfers`）**：
   - 篩選 `transfers.to_account_id = target_account_id`
   - 增加金額：$+\sum(\text{to\_amount})$
3. **花費表（`expenses`）**：
   - 篩選 `expenses.account_id = target_account_id`
   - 減少金額：$-\sum(\text{amount})$
   - *註：信用卡帳戶若記錄花費，則花費代表累積之應繳負債（若餘額定義為資產，則為負向資產；若定義為待繳帳單，則為待繳金額）。*
4. **轉出款項（`transfers`）**：
   - 篩選 `transfers.from_account_id = target_account_id`
   - 減少金額：$-\sum(\text{from\_amount})$
5. **投資交割款項（`investment_transactions`，僅限券商交割戶）**：
   - 篩選 `investment_transactions.account_id = target_account_id`
   - 為避免重複計算：
     - 若為 `cash_dividend` 或 `capital_reduction`，其現金流入已經在 `incomes` 中建立入帳列者（已透過 `incomes.investment_transaction_id` 計算），則**不**自本表重複累加。
     - 若為 `buy`（買進）：交割扣款，扣除金額 $-\sum(\text{net\_cash\_amount})$。
     - 若為 `sell`（賣出）：交割收款，增加金額 $+\sum(\text{net\_cash\_amount})$。

---

### 2. 投資持有股數與平均成本衍生邏輯

針對特定投資標的（給定 `target_id`），將其所屬之 `investment_transactions` 依照 `transacted_at ASC, id ASC` 依序回放，採用**加權平均法（Weighted Average Cost）**動態推算任一時間點之「持有股數」與「每股平均成本」：

#### (1) 8 種交易型態之股數與成本遞推規則
初始狀態：持有股數 $S = 0$，總投入成本庫存 $C = 0$。

1. **買進 (`buy`)**：
   - 新股數：$S_{\text{new}} = S + \text{shares}$
   - 新總成本：$C_{\text{new}} = C + (\text{shares} \times \text{price\_per\_share} + \text{fee} + \text{tax})$
   - 每股平均成本：$\text{avg\_cost} = C_{\text{new}} / S_{\text{new}}$
2. **賣出 (`sell`)**：
   - 驗證條件：$\text{shares} \le S$（由 API 在寫入前檢查，不得使剩餘股數小於 0）。
   - 新股數：$S_{\text{new}} = S - \text{shares}$
   - 新總成本：依照當前每股平均成本等比例結轉扣除，$C_{\text{new}} = C - (\text{shares} \times \text{avg\_cost})$
   - 每股平均成本：維持不變 $\text{avg\_cost}$（若 $S_{\text{new}} = 0$，則 $C_{\text{new}} = 0$, $\text{avg\_cost} = 0$）。
3. **配股 / 股票股利 (`stock_dividend`)**：
   - 無需額外付出資金，但獲取新股數。
   - 新股數：$S_{\text{new}} = S + \text{shares}$
   - 新總成本：$C_{\text{new}} = C + \text{fee}$（通常手續費為 0，總成本維持不變）。
   - 每股平均成本：被稀釋為 $\text{avg\_cost} = C_{\text{new}} / S_{\text{new}}$。
4. **股息再投入 (`dividend_reinvestment`)**：
   - 將配發之股利自動再買入股份。
   - 新股數：$S_{\text{new}} = S + \text{shares}$
   - 新總成本：$C_{\text{new}} = C + (\text{shares} \times \text{price\_per\_share} + \text{fee})$
   - 每股平均成本：$\text{avg\_cost} = C_{\text{new}} / S_{\text{new}}$。
5. **股票分割 (`split`)**：
   - 依分割比例放大股數（例如 1 股分割為 2 股，比例為 $1 \to 2$）。
   - 放大倍率：$R = \text{split\_ratio\_to} / \text{split\_ratio\_from}$
   - 新股數：$S_{\text{new}} = S \times R$
   - 新總成本：總投入成本不變 $C_{\text{new}} = C$
   - 每股平均成本：反向縮小為 $\text{avg\_cost} = C / S_{\text{new}}$。
6. **股票合併 (`reverse_split`)**：
   - 依合併比例縮減股數（例如 2 股合併為 1 股，比例為 $2 \to 1$）。
   - 縮小倍率：$R = \text{split\_ratio\_to} / \text{split\_ratio\_from}$
   - 新股數：$S_{\text{new}} = S \times R$
   - 新總成本：總投入成本不變 $C_{\text{new}} = C$
   - 每股平均成本：反向提高為 $\text{avg\_cost} = C / S_{\text{new}}$。
7. **減資 (`capital_reduction`)**：
   - 分為「退還股款減資」與「彌補虧損減資」：
     - **退還股款減資**：換股比例 $R = \text{split\_ratio\_to} / \text{split\_ratio\_from}$（如銷除 20% 股份，比例為 $1000 \to 800$）。
       - 新股數：$S_{\text{new}} = S \times R$
       - 退回現金：$\text{net\_cash\_amount}$
       - 新總成本：$C_{\text{new}} = C - \text{net\_cash\_amount}$
       - 每股平均成本：$\text{avg\_cost} = C_{\text{new}} / S_{\text{new}}$
     - **彌補虧損減資**：僅銷除股數無退回現金，新總成本不變，每股平均成本相應調整。
8. **現金股利 (`cash_dividend`)**：
   - 持有股數不變 $S_{\text{new}} = S$。
   - 現金股利作為收益，直接進入 `incomes` 入帳表。持股成本庫存可維持不變，或視個人會計偏好選擇扣減成本。

## 肆、統一發票期別與獎金處理機制

### 1. 統一發票期別由開立日決定之規則

台灣統一發票制度為**雙月一期**，全年度共有 6 個開獎期別。統一發票的期別必須根據發票開立日（`issued_at`）的時間嚴格推導：

#### (1) 期別劃分規則
| 開立月份 | 所屬雙月期別名稱 | 西元期別代碼（`period`） | 說明 |
| :---: | :---: | :---: | :--- |
| 1 月、2 月 | 1-2 月期 | `YYYY02` | 當年第 1 期，開獎日為當年 3 月 25 日 |
| 3 月、4 月 | 3-4 月期 | `YYYY04` | 當年第 2 期，開獎日為當年 5 月 25 日 |
| 5 月、6 月 | 5-6 月期 | `YYYY06` | 當年第 3 期，開獎日為當年 7 月 25 日 |
| 7 月、8 月 | 7-8 月期 | `YYYY08` | 當年第 4 期，開獎日為當年 9 月 25 日 |
| 9 月、10 月 | 9-10 月期 | `YYYY10` | 當年第 5 期，開獎日為當年 11 月 25 日 |
| 11 月、12 月 | 11-12 月期 | `YYYY12` | 當年第 6 期，開獎日為次年 1 月 25 日 |

#### (2) 數學與程式推導公式（由 API 在寫入前檢查與計算）
設開立日 `issued_at` 提取之西元年份為 $Y$（整數，如 2026），月份為 $M$（整數，範圍 $1 \le M \le 12$）：

$$\text{期別偶數月份} = \left\lceil \frac{M}{2} \right\rceil \times 2$$

$$\text{期別代碼（period）} = Y \times 100 + \left( \left\lceil \frac{M}{2} \right\rceil \times 2 \right)$$

- **範例 1**：開立日為 `2026-01-15` $\to M = 1$，$\lceil 1/2 \rceil \times 2 = 2$ $\to$ 期別為 `202602`。
- **範例 2**：開立日為 `2026-10-05` $\to M = 10$，$\lceil 10/2 \rceil \times 2 = 10$ $\to$ 期別為 `202610`。
- **範例 3**：開立日為 `2026-11-01` $\to M = 11$，$\lceil 11/2 \rceil \times 2 = 12$ $\to$ 期別為 `202612`。

### 2. 開獎獎金存放於資料表與中獎入帳機制

1. **獎金存放於獨立資料表**：
   - 獎金金額完整記錄於 `invoice_prize_tiers.reward_amount`，設計說明與後端程式碼中絕不寫死獎金數字。
   - 現行標準獎項與資料表初始化範例：
     - `special_prize`（特別獎）：$10,000,000$ 元
     - `grand_prize`（特獎）：$2,000,000$ 元
     - `first_prize`（頭獎）：$200,000$ 元
     - `second_prize`（二獎）：$40,000$ 元
     - `third_prize`（三獎）：$10,000$ 元
     - `fourth_prize`（四獎）：$4,000$ 元
     - `fifth_prize`（五獎）：$1,000$ 元
     - `sixth_prize`（六獎）：$200$ 元
2. **對獎與中獎更新流程**：
   - API 將特定發票之 `invoice_number` 與對應期別之 `invoice_draws` 比對。
   - 若符合中獎條件，將 `invoices.prize_tier_id` 指向對應之獎項資料列。
3. **中獎獎金入帳限制**：
   - 中獎後若領取獎金入帳，於 `incomes` 表新增一筆紀錄：
     - `account_id`：存入獎金之帳戶。
     - `category_id`：指向「統一發票中獎」分類。
     - `amount`：取自 `invoice_prize_tiers.reward_amount`（扣除法定印花稅/所得稅後實得金額，或記錄票面全額）。
     - `invoice_id`：填入該張發票 ID。
   - **資料庫約束保護**：因 `incomes.invoice_id` 設有 `UNIQUE` 約束，保證一張中獎發票在資料庫層級**絕對無法重複領取或產生兩筆以上之入帳**。
